# Android 输出端缓冲越来越小：原因与修复

## 现象

Android 设备作为「输出端」、Windows 作为「音源端」时，输出中心里这一路的
`xxx ms 缓冲` 会缓慢但持续地变小（常见于 240 ms 设定值掉到 100 ms 以下），
有时降到 0 后画面仍显示在线，但声音变成断续或完全静音，只能停止输出再重启。
（这是 Windows 音源 → Android 输出方向的观察；反向组合未实测。）

## 根因

这不是网络抖动，而是**采集端时钟与播放端时钟的速率差**在积少成多地吃掉抖动缓冲。

- Windows 音源把「第 n 个音频包」的时间戳写成 `n × 5000 µs`（高音质为 120 帧 /
  2.5 ms），时间戳的速率等于它的采集声卡/虚拟声卡（这台机器上是 VB-CABLE）的
  采样时钟；
- Android 输出端用 AudioTrack 的播放时钟消费音频，两者是**两颗不同的晶振/时钟域**；
- 1.1.6/1.1.7 里唯一补偿这个速率差的机制是 `MixEngine.render()` 中按 ±1/±2 帧滑动
  混音游标，即每 480 帧只允许 ±2 帧，**只能吸收 ±0.42%**；
- 音源端 `ClockSynchronizer` 的偏移量按 2 ms/s（0.2%）渐进修正，当源端时间戳
  自身速率偏慢时，还会额外留下时间戳滞后。

只要两端有效速率差超过约 0.3%–0.5%（取决于源端偏移校正的剩余滞后），缓冲就会
持续变小：0.5% 的差值下 240 ms 会在一分多钟里掉到 150 ms 左右，并在混音游标累计
落后墙钟 300 ms 时被重锚清空、直接归零。物理声卡之间通常只有几十 ppm，不会触发；
但虚拟声卡（VB-CABLE / Voicemeeter / Scream）、蓝牙、USB 声卡、部分设备的
AudioTrack 重采样链路都可能超出这个范围——所以现象只在「Windows 做音源」时明显。

同时代码里还有两个把问题放大的缺陷：

1. **归零后无法自愈**：缓冲耗尽后 `hasDataAfter()` 变为 false，漂移控制器因为
   `active == 0` 而停止工作，此后每个包的时间戳都落在混音游标之后，被
   `SourceTimeline.mixInto()` 直接丢弃。输出端会一直静音，直到停止/重启输出。
2. **300 ms 重锚会误触发**：`push()` 里判断「游标落后墙钟 300 ms」就前移
   `startUs` 并清空缓冲。这个条件原本用于输出线程卡死，但漂移微调本身就会让
   游标落后墙钟，累积到 300 ms 后会清掉刚补回来的数据，表现为周期性卡顿。

反方向（音源比播放端快）则相反：微调追不上时缓冲会一直变大，延迟无限增长
（仿真中 +1% 的速率差在 4 分钟内把 240 ms 缓冲推到 1.2 s），而重锚只在游标落后
时触发，因此不会被回收——这是 1.1.7「输出端延迟越来越大」的另一面。

## 1.1.9 的修复

`src/android/app/src/main/java/com/samevoice/mobile/HostEngine.kt` 的 `MixEngine`：

- 用**分数速率微调**替换 ±2 帧整数微调：混音游标按 `1 + trim` 推进，
  `trim` 由缓冲偏差经两级平滑后给出，范围 **±3%**；小数部分用 `rateCarry`
  累积，保证平均速率精确，不会出现「每块都跳 2 帧」的规律性咔哒声。
- **移除**基于混音游标落后的 300 ms 重锚，改为：
  - `writtenProgressUs` 检测输出线程是否真的停顿（>500 ms 没有写成功）；
  - `emptySinceUs` 检测缓冲是否真的持续为空（>1 s）；
  - 命中任一条时，把当前包的时间戳重新锚定到「游标 + 目标缓冲」，并清空已过期队列。
    这样输出线程卡死或时钟差大到 3% 以上时能自动回到目标延迟，而不是永久静音。
- 目标缓冲、主音量、每路音量的对外行为不变；UI 显示的 `xxx ms 缓冲` 仍然是
  真实的抖动缓冲（内容帧数）。

## 验证

`tools/timeline-sim/sim.py` 把 `MixEngine` / `SourceTimeline` 和 Windows 端的
时间戳逻辑 1:1 移植成 Python 仿真，可复现上面的结论（240 s，目标 240 ms）：

| 源端速率差 | 1.1.7 结果 | 1.1.9 结果 |
| --- | --- | --- |
| 0% | 249.8 ms | 235 ms |
| −0.1% | 245.8 ms | 235 ms |
| −0.3% | 213.4 ms（已开始变小） | 231.6 ms |
| −0.5% | **0 ms，15k 丢包，永久静音** | 226.7 ms |
| −1% | **0 ms，30k 丢包，永久静音** | 214.2 ms |
| −2% | **0 ms，41k 丢包，永久静音** | 189.1 ms |
| +1% | 1212 ms 且持续变大 | 260.6 ms |

```powershell
python tools/timeline-sim/sim.py --compare --seconds 240
```

真机验收：Android 输出 + Windows 音源，连续播放 10 分钟，`缓冲` 应稳定在设定值
附近（±3% 时钟差时会有几十毫秒的稳态偏差，属正常），不再单向下降；中途拔网线
3 秒，恢复后应能自动回到目标缓冲。

## 还需要注意

- 本次只改了 Android 端。已用仓库内的 `.toolchain/`（JDK 17 + Android SDK）构建出
  `dist/android/SameVoice-1.1.9.apk`（versionCode 15，演示签名），可直接侧载；
  重新构建见 README 的「从源码构建 → Android」一节。
- Windows 端 `ClockSynchronizer` 目前只估计偏移量、按 2 ms/s 渐进修正。作为
  可选的后续改进，可以在音源端对最近 N 次 ping 的偏移量做线性拟合，估计出
  「源端采样时钟 / 主机时钟」的速率比并直接乘到时间戳上，这样时间戳本身就能
  跟住主机的时钟速率，Android 端的微调只需处理 DAC 与系统时钟的残余差。
- 临时规避（不升级 APK 时）：把「手动缓冲延迟」调大（例如 600–800 ms）只能延长
  耗尽时间；缓冲掉到 0 后必须停止并重新启动输出才能恢复；改用「同步优先」+
  16-bit、避免手机蓝牙输出、优先使用物理声卡采集（而不是 VB-CABLE 等虚拟声卡）
  可以减小速率差。
